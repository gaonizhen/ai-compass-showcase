云端产物（WorkBuddy / 千问）

WorkBuddy 的 个人记账本.html、调研报告、todo-fixed.html 都在云端产物面板； 千问给出 presigned_url 可直取。两者都需要额外一步"把文件拿回来"。

方法论教训（已写进方法记录）：只看对话截图判卷，会系统性低估交付物落在文件系统的产品。 我在同一个坑里踩了两次——S7 只看文件名没打开图就断言"缺解释"；S3 只看对话就断言"图表不能导出、没有计算过程"。 两次的证据其实都在磁盘上。规则：判卷须同时检查对话侧与文件系统侧。

③ 自证可信度：产品自己做的"实测"值不值得信

产品自证行为走查员复算评级
WorkBuddy主动声明"已验证（无头浏览器实测）：16 条示例数据 → 7 个扇区、合计 ¥6,716.47" 其验证方式与我方 harness 一致；离线渲染与数值均复现通过 ★★★ 主动自证且方法一致
千问办公称"我用一个模拟 DOM 跑了一遍"，给出"click 监听数 1→2→3"并断言真实 DOM 会派发多次 真实浏览器对照实验：同一函数引用注册 3 次 → 点击触发 1 次（浏览器去重）——该结论不成立 ★ mock 当实测，结论失真
豆包工作 / ChatGPT Work豆包 S7 未跑代码但机制判断正确；ChatGPT 称"已通过语法检查和连续点击测试" ChatGPT 的声明与 harness 结果一致 ★★ 声明与实测相符
"我自己实测过" ≠ "实测可信"——关键要看它在什么环境里证。 千问用 mock DOM 产出了一个真实浏览器里不存在的现象；WorkBuddy 用真无头浏览器，结论可复现。 这条与批次一"链接都能打开、内容却对不上"（Kimi）属同一族：验证动作看起来充分，验证对象不忠实。

对批次一三条策略建议的增量

批次一给豆包工作 PM 的三条建议（反幻觉心智 / 工程交付严谨性 / 用量透明层）在批次二得到了新证据。

建议 1「忠实性 + 引用健康度产品化」→ 证据增强

批次一只有 Kimi 一家反面样本；批次二补到两家：千问 S4 夸大交付属性（"零依赖"vs Google Fonts）、 ChatGPT S5 把门户首页当报道引用。"自述不可靠"是这条赛道的结构性问题，不是个别产品缺陷。

建议 2「补齐工程交付严谨性」→ 出现了可对标的样板

WorkBuddy 把 ECharts 内联进 1MB 单文件、真正离线可用——这就是"外链资源 = 0"发布门禁 落地后的样子。豆包若补上这条门禁，可直接对标这一实现。

建议 3「用量透明层」→ 品类内仍无人做好

四家里只有两家显示积分余额，且没有一家做任务级消耗可视化。批次一建议的"用量透明层" 在批次二依然空位——这既是豆包的机会，也说明这条建议的窗口仍然开敞。

新增建议 4（面向品类）：「自证须可复算」

产品开始主动输出"我已验证"的声明。建议把自证做成可复算的证据（附 harness / 复现步骤）， 而不是一句结论——否则会像千问那样，用 mock 环境产出真实环境不存在的现象，反而损伤信任。

走查执行摘要

2026-10-05 ~ 10-06 · 四家 × 五类任务（S1 写周报 / S3 数据分析 / S4 网页生成 / S5 信息调研 / S7 修 bug）， 统一 prompt 逐字一致、预埋事实抓幻觉（销售数据 3 处、bug 代码 2 处）。 本批次全部任务由走查员通过 CDP 驱动真实浏览器执行（WorkBuddy / 千问）， 或由用户人工执行 + 走查员判卷（ChatGPT Work 桌面 App）； 修复代码与网页交付物均经真实浏览器 harness 实测（tools/verify-s4.py、tools/verify-s7.py）。

局限声明（如实）

  • 仅豆包具备跨期对照：其余三家为单次快照，不做稳定性外推；
  • 成本不可比：本批次四家不提供任务级、可比口径的消耗数据（见"成本维度"节）；
